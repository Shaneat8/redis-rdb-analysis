## Experiment 1 — CRC64 Checksum Toggle: Metrics

Workload: 200,000 SET commands, value sizes randomly drawn from {16, 64, 256} bytes.
Save command: synchronous SAVE (foreground) — chosen so the timer captures only the
serialization+fsync path, with no fork() / COW noise. 3 trials each, median reported.

| Metric                       | Baseline (rdbchecksum yes) | Modified (rdbchecksum no) | % Change |
|------------------------------|----------------------------|---------------------------|----------|
| SAVE time (median, 3 trials) | 0.2933 s                   | 0.3189 s                  | +8.74%*  |
| RDB file size                | 24,678,103 bytes           | 24,678,103 bytes          |  0.00%   |
| used_memory                  | 40,962,552 B (39.06 MB)    | 40,962,520 B (39.06 MB)   | ~0.00%   |
| used_memory_rss              | 50,610,176 B (48.27 MB)    | 49,451,008 B (47.16 MB)   | -2.29%   |
| Keys loaded after corruption | 0 (LOAD ABORTED)           | 200,000 (silent accept)   |  N/A     |
| RDB last-save status         | ok                         | ok                        |  same    |
| Errors during corrupt-load   | "Wrong RDB checksum ...    | none                      |  N/A     |
|                              | Aborting now."             |                           |          |

* The +8.74% difference is well within run-to-run noise on this workload (range
  ≈ 60 ms across both groups). The signal that CRC64 is "free" is stronger than
  any speedup signal — see analysis.md for why.
