## Experiment 3 — Log / Behaviour Diff

### Server log diff (ordered events during BGSAVE)

  Both runs emit the same event sequence:

    M ... * Background saving started by pid <child>
    C ... * DB saved on disk
    C ... * RDB: 4 MB of memory used by copy-on-write
    M ... * Background saving terminated with success

  No diff in event content or count. The only diff is timing of these
  events relative to the storm:
    baseline:  BGSAVE start at t=11.0s, child exits at t=12.1s (1.1 s)
    modified:  BGSAVE start at t=12.5s, child exits at t=13.8s (1.3 s)
  Both well below the storm window (~7–8 s), so the storm spans the
  entire BGSAVE and continues afterwards.

### COW report (identical)

  baseline:   RDB: 4 MB of memory used by copy-on-write
  modified:   RDB: 4 MB of memory used by copy-on-write
  → 4,673,536 bytes in both cases. The storm's writes targeted *new*
    keys (`sk:*`), which Redis allocates into pages that did not exist
    in the snapshot. Only allocator metadata and dict bucket-array
    resizes were faulted in — and most of those would have been
    triggered by the storm regardless of BGSAVE.

### Latency diff (PING samples during storm)

  baseline:    p50=5.72 ms  p95=14.59 ms  p99=16.77 ms  max=22.71 ms
  modified:    p50=5.64 ms  p95=16.14 ms  p99=21.47 ms  max=21.91 ms

  Modified is slightly *worse* on p95/p99. See analysis.md for why
  incremental fsync can hurt at this dataset size.

### Throughput diff (storm)

  baseline:    7.34 s for 200k writes  (≈ 27.2 k ops/s)
  modified:    8.43 s for 200k writes  (≈ 23.7 k ops/s)
  → -12.9% throughput with incremental fsync on, in this regime.

### File size diff

  baseline dump.rdb: 99,597,280 bytes
  modified dump.rdb: 99,597,280 bytes
  → Identical. The fsync mode does not change RDB content.
