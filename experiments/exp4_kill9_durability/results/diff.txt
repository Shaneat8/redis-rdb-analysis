## Experiment 4 — Log / Behaviour Diff

### File-on-disk diff at moment of kill -9

  baseline (RDB-only):
    /tmp/exp4_baseline/
    -rw-r--r--  93 dump.rdb           ← initial empty snapshot, untouched
    -rw-r--r-- 1076 server.log

  modified (RDB + AOF everysec):
    /tmp/exp4_modified/
    -rw-r--r--    93 dump.rdb         ← initial empty snapshot, untouched
    -rw-r--r-- 424097 appendonly.aof  ← every acked write captured
    -rw-r--r--   1076 server.log

  → The AOF carries the entire write history; the RDB carries
    nothing past the initial snapshot.

### Server-startup log diff (after restart)

  baseline:
    * Loading RDB produced by version 6.2.14
    * DB loaded from disk: 0.000 seconds
    * Ready to accept connections
  → 0 keys reloaded.

  modified:
    * DB loaded from append only file: 0.014 seconds
    * Ready to accept connections
  → 12,062 keys reloaded from AOF.

  Note: when both RDB and AOF exist, Redis uses the AOF as the source
  of truth (via `aof-use-rdb-preamble`'s default behaviour). The RDB
  is consulted only if AOF is missing or unloadable.

### Behaviour diff (recovery)

  baseline DBSIZE_AFTER_RESTART = 0           (LOSS = 26,336 writes)
  modified DBSIZE_AFTER_RESTART = 12,062      (LOSS = 0 writes)

### Workload-throughput diff (during write phase)

  baseline:    26,337 SETs in ~3 s   ≈ 8,779 ops/s
  modified:    12,062 SETs in ~3 s   ≈ 4,021 ops/s

  AOF-on slowed the writer by ~54%, because every SET also goes
  through the AOF append path (`feedAppendOnlyFile`) which copies
  the command to an AOF buffer that the background fsync thread
  drains. On this fast in-memory FS the difference is mostly the
  per-command serialisation cost into the AOF buffer, not disk I/O.
