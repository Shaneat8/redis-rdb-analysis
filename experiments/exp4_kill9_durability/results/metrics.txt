## Experiment 4 — kill -9 Durability Gap: Metrics

Procedure:
1. Start Redis with persistence config (RDB-only, or RDB+AOF everysec).
2. Trigger an initial BGSAVE so a baseline RDB exists on disk.
3. Run a synchronous writer for ~3 seconds:
     for i in 0..N: r.set(f"w:{i}", str(i))
   Each SET is acknowledged before the next is sent.
4. `kill -9` the redis-server process (no SIGTERM, no shutdown hook,
   no chance for buffered writes to flush).
5. Restart with the same config; query DBSIZE and the highest
   surviving `w:i` key (binary search).
6. Report `data_loss = last_acked_before_kill − last_surviving_after_restart`.

### Why baseline lost everything

The only RDB on disk was the *initial* one taken before the writer
ran. RDB persistence is point-in-time: nothing after the last BGSAVE
is durable. The writer never crossed a `save` threshold (we set
`save ""` to disable auto-snapshots) and never issued another BGSAVE.
A `kill -9` skips Redis' shutdown hook (`prepareForShutdown()`), so
no synchronous final SAVE was performed. Result: full loss of the
write window.

### Why modified lost nothing on this trial

`appendfsync everysec` flushes the AOF buffer to disk via fsync()
once per second on a background thread. A trial that happens to be
killed shortly *after* an fsync sees little or no loss; one killed
shortly *before* the next fsync would lose up to 1 second of writes.
The everysec window's *theoretical maximum* loss is the volume of
writes between fsyncs (~1 s × throughput); on this trial the kill
happened to fall within ~50 ms of an fsync (AOF mtime was within
50 ms of the kill timestamp), so loss = 0.
